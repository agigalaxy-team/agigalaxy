# Galaxy discovery native stack

This is a source installation template with dated implementation notes, not a current host state report. Existing installations use their recorded images, protected configuration and volumes; a controller-only patch must not rerun the initial migration/bootstrap command. Build the modified OpenPanel source using [the source-context instructions](../../services/galaxy-discovery/SOURCE_BUILD.md).

This stack connects native OpenPanel, Gorse and Meilisearch to the existing
Galaxy service. It is operated by the primary deployment owner on the existing
Oracle server. It does not create a separate staging business or change Galaxy
file storage, TTL, capacity, production credentials or existing containers.

## Native sources and fixed release scope

| Engine | Runtime | Source actually reviewed |
| --- | --- | --- |
| Meilisearch | `getmeili/meilisearch:v1.55.0`, community distribution | [Official v1.55.0 release](https://github.com/meilisearch/meilisearch/releases/tag/v1.55.0); MIT community keyword search/index/tasks, no enterprise functions |
| Gorse | `zhenghaoz/gorse-in-one:0.5.11` | [Official v0.5.11 source](https://github.com/gorse-io/gorse/tree/v0.5.11), including `server/rest.go` and `config/config.toml`; Apache-2.0 |
| OpenPanel | public `lindesvard/openpanel-api:2` and `openpanel-worker:2` | [Public self-hosting source at cd24bb8](https://github.com/Openpanel-dev/openpanel/tree/cd24bb838301df1a9087e2e132b344e5b8a99963), AGPL-3.0; not supporter-first 3.x |

OpenPanel's `:2`, and database image tags, are release-line references rather
than immutable digests. On the actual first pull, the primary owner records
RepoDigests and supplies the remote image override. Do not replace the selected
public line with 3.x based on a similarly named image or newer README.

The first real launch rejected several recommenders with `ranker.type=none`.
The supplied file now selects one native collaborative candidate source and
keeps native neighbor/latest fallbacks. Matrix factorization is the engine's
local statistical recommender. LLM/embedding/reranker endpoints, keys and model
names are blank; no model provider is contacted.

The first Redis cache startup failed on `FT._LIST`: v0.5.11's Redis adapter
requires RediSearch. The final configuration uses its native PostgreSQL cache
adapter in the dedicated Gorse database, with `galaxy_cache_` table prefix. It
uses the standard `btree_gin` extension. The old Redis volume is preserved behind
the optional `legacy-cache` profile; no Redis 8 or separately licensed module is
introduced. OpenPanel continues to use its separate ordinary Redis for its own
native queue. The corrected Gorse PostgreSQL data/cache readiness was actually
reported ready by the primary deployment owner.

## Configuration and startup

`compose.yaml`, `gorse.toml`, `clickhouse-config.xml` and the gateway build context
are nonsecret source. `runtime.env.example` documents names only. Generate independent
high-entropy keys and hex database passwords into a protected file outside the
repository; never print `docker compose config`, a resolved environment, or
bootstrap secrets into evidence. These services must use their new data volumes,
not Galaxy's existing application database or another service's Redis.

Host access is explicitly loopback-only: Meili `17700`, the Gorse guard `18088`,
OpenPanel API `18001`. Confirm host availability before startup. The normal shared
Docker network supports these loopback bindings. The native Gorse network stays
`internal`; no native API/dashboard port is published. No reverse proxy or public
dashboard is added by this stack.

The API container runs OpenPanel's own migrations. After it becomes healthy,
execute `node /opt/galaxy/bootstrap-openpanel.mjs` inside it. The bootstrap imports
the exact native generated TS Prisma client and original scrypt helper. It creates
only the configured organization/project, its native non-login service-owner
membership and distinct project-bound read/write clients. The owner membership
is required: upstream's hourly delete cron treats an organization with no
`org:admin` member as orphaned, including self-hosted organizations. No native
User/Account/Session/Invite or paid subscription is fabricated for this ownership
relation. Existing ownership or credential drift fails rather than rotating any
credential. The upstream generator is `prisma-client`, with output
`packages/db/src/generated/prisma/client.ts`; the default `@prisma/client` entry
is not generated by this image. The first actual attempt using that default entry
failed and is preserved in the deployment evidence.

There is no SMTP/provider key, model key, OpenPanel registration, invitation,
formal experiment, predicted message or automatic user outreach configured.

## Galaxy runtime injection

The primary server constructs:

```js
const discovery = createDiscoveryRuntime({
  db, endpoint, forum, accounts, permissions,
  config: {
    meilisearch: {url, apiKey, index: 'galaxy_public_community'},
    gorse: {url, apiKey}, // The separate guard key, never the native key.
    openpanel: {url, clientId, clientSecret, readClientId, readClientSecret, projectId},
  },
});
```

Import from `packages/galaxy-official/src/discovery-runtime/runtime.mjs`.
An absent engine config stays not-connected; a configured URL alone is not a
health or integration success. Runtime credentials remain inside Galaxy's server
or worker and never reach a browser. The Meili client waits for native task
success before acknowledging an indexing step.

Migration source is `discovery-runtime/schema.mjs`, reserved version **106**:
`discoveryRuntimeMigrationSql`, `discoveryRuntimeApiGrantsSql` and
`discoveryRuntimeWorkerGrantsSql`. The registry and role-file owner applies these
centrally. No event/file retention period or deletion worker is introduced.

The worker uses the same configuration plus `sourceReadOnly:true`. It consumes
the original anonymous forum source qualification with row locking disabled,
without receiving UPDATE permission on authorizations. Construct
`new DiscoveryWorker(runtime)`. Initialize the runtime once, process bounded
`seedBatch()` pages for initial discovery/reconciliation, then call `indexOne()`
and `deliverOne()` from the existing worker cycle. Finish a reconciliation sweep
before restarting its cursor. Its repeat interval is an operational scheduling
choice, not a user storage TTL. `indexOne()` also queues indexed source expiries.
Source, permission, section, governance, curation, tag and revocation triggers
enqueue invalidation; public searches/recommendations still re-read current
source eligibility on every returned item.

The existing standalone worker does not need the API service graph. Import
`createDiscoveryReadOnlySource` from `discovery-runtime/public-content-source.mjs`
and pass `{db,endpoint,now,readGrant,forumPolicy,moderatorIds,identityProviders}`;
then inject the returned `source` into the runtime. Use the API's actual moderator
list and provider issuer/client metadata. It constructs only the original forum,
permission, account-registry and governance readers. The anonymous path performs
no account authorization write, attachment read or signing operation. Legacy
governance independence still uses its original account-link checks.

## Purpose boundary and actual collector coverage

Only closed page keys enter site usage analysis: `home`, `community`, `find`,
`account`, `help`, `download`. The collector maps actual Galaxy routes locally;
it transmits no arbitrary URL, query string, account ID or visitor ID. The server
assigns account identity from its official session, or a signed HttpOnly visitor
session cookie. An in-flight anonymous event cannot become another account event
through an ambient cookie change.

OpenPanel receives `site-usage-analytics`. This is broader than the recommendation
purpose. Current automatic collectors actually send:

| Event | Actual entry point | Recommendation target |
| --- | --- | --- |
| `pageview` | `main.tsx` path effect, six closed page categories | none |
| `search` | Native community search in existing `/app/find` | none |
| `search-click` | Actual qualified community result link | Gorse click |
| `content-view` | Successfully read current public forum post/reply | Gorse view |
| `content-exposure` | Existing discovery page recommendation card, >=50% visible | none |
| `content-click` | Recommendation link | Gorse click |
| `not-interested` | Explicit recommendation preference | immediate local exclusion + native feedback |
| `content-bookmark` | Acknowledged account bookmark save of a currently anonymous-readable forum post | Gorse bookmark |
| `content-participate` | Acknowledged account post / next version / reply publication, including original receipt recovery | Gorse participate |

Confirmed bookmark/publication callbacks use the original operation ID as the
stable event ID. An anonymous source read obtains the actual current version;
publication must still match the acknowledged exact version/revision. A fresh
official session must belong to the original account. Button clicks, unknown
write outcomes, unsaves and saved-state refreshes produce no success event.
The existing bookmark feature supports forum posts, not individual replies;
private-message and other bookmark kinds are excluded from these collectors.
Collection failure never changes the acknowledged business result.
Further normal pages/business usage can add reviewed page keys/event codes from
their actual source actions. The current six are not a permanent analytics scope.

Every content event references exact `{kind,id,version}` and must pass the
original current anonymous reader. General page visits, searches and exposures
are never implicitly Gorse training. Private chat text, case/report/evidence
material, notices, system mail, their open/click data and derived labels have no
accepted schema or collector here. Ordinary base usage on additional sensitive
pages would require a separate closed metadata-only page key, never content
reuse or recommendation delivery.

Source qualification checks version, audience, section, withdrawal, expiry and
all effective governance overlays. Meili returns only candidate IDs/revisions;
Galaxy returns fresh source text, not cached engine snippets/totals. The indexed
revision includes current public curation to prevent removed tags matching stale
searches. Ineligible Gorse items are deleted with their feedback; `IsHidden` alone
is not treated as training removal. Negative preference is checked again by
Galaxy before returning recommendations. Native cold-start/latest fallback is
labelled as such rather than inventing a personalized reason.

## HTTP and controlled tools

The exact HTTP adapter is `discovery-runtime/http.mjs`:
`createDiscoveryHttp({websiteOrigin,visitorSecret,secureCookies:true})` and
`.dispatch({discovery,officialAccounts,authorizeOperator,request,response,url,send,requestId})`.

| Path | Method | Closed input / authorization |
| --- | --- | --- |
| `/v1/discovery/config` | GET | no query; visitor cookie and CSRF token |
| `/v1/discovery/events` | POST | JSON <=2048 bytes; exact website Origin, discovery CSRF; official account ID/CSRF when logged in |
| `/v1/discovery/search` | GET | `q`, optional `topic`, numeric `after`, `limit`; current anonymous public source |
| `/v1/discovery/recommendations` | GET | optional `mode`, `topic`, `limit`; official cookie identity or anonymous visitor |
| `/v1/operations/discovery/analytics` | GET | `kind`, optional `days`, `accountId`; fresh `analytics.read` before and after native read |

Unknown/duplicate query keys and unknown event fields are rejected. CORS must
allow only configured website origins and exact discovery/account headers.
Bearer host credentials are not accepted as an analytics account identity.

Analytics `kind=overview|retention|paths|account` calls public 2.x native Insights
REST handlers with project-bound read credentials. `kind=business` uses the
same read client and native `GET /export/charts` / `ChartEngine` with four
event series and the `site-usage-analytics` purpose filter. It returns native
per-series sums for reading, searching, bookmarking and participating, for the
current and previous equal windows. This internal chart query introduces no
Galaxy export endpoint. Counts are event occurrences, not people or sessions.
The basis records disjoint `[from,to)` windows with second precision. Missing
or invalid native sums remain `null`; engine errors are never converted to 0.
The native events export's `totalCount` is unsuitable here because its current
count query truncates supplied bounds to dates.

Native overview returns
`summary` and `series` (including `unique_visitors`, `total_sessions`,
`total_screen_views`). Cohort is the native last-12-week weekly, any-event,
`on_or_after` basis. Its `profile_id != device_id` condition includes Galaxy's
`visitor:` and `account:` profiles, so the unscoped result is mixed profile
retention. The unmodified upstream cohort REST handler exposes no account-prefix
filter. Native path values are
session-path transitions in a selected top-path subset, not account conversion
or whole-window usage totals. Profile metrics are native lifetime. These
different bases are returned explicitly.

The Galaxy account-scope native patch adds `scope=accounts` with an optional
UUID `accountId` only for cohort and user_flow. The same Galaxy analytics endpoint
accepts that scope only with `kind=retention|paths`; overview/business stay
unscoped, and the existing account kind still requires its accountId. A scoped
response must acknowledge the exact scope and selected account in native
headers. Older engines that silently ignore the query fail closed rather than
being mislabeled. There is no identify/alias operation or anonymous backfill.
Scoped cohort is first qualified activity in the native 12-week window, not
registration retention; its ClickHouse default timezone name remains unknown
unless actually provided. Scoped flow uses account+session grouping and its
actual native project timezone. The DTO keeps the native data structures and
records account population, Top-path scope and timezone source separately.
Activate the matching patched native image before enabling the new scope in
Galaxy. Its complete corresponding source is provided at the fixed
[Galaxy source archive](https://agigalaxy.org/open-source/openpanel-public2-galaxy-accounts-20261023/source.tar.gz);
Galaxy returns that same fixed link only on acknowledged scoped responses.
No unmeasured active/retention values or historical backfill are invented.
AgentOS must call a Galaxy controlled read tool, never a native engine. An
execution identity is not converted into a fake administrator; analytics remains
closed until its own authority bridge actually supports the requested read.
For already attested task resources, internal
`searchSelected(input,[{kind:'post'|'reply',id}])` requires a nonempty selected
scope. It filters native candidates by those exact keys and checks the selected
set again before reading/returning source content. The execution gateway derives
the selection from current task authority, not model arguments. The current Agno
tool returns selected IDs/versions only and uses its separately pinned read tool
for content. This is not an additional public endpoint or an event collector.

## AI-agent deployment and verification

1. Discover the current host/project configuration and protected env by metadata.
   Reuse the existing host; do not create billable resources or restart unrelated
   application containers. The primary deployment owner performs remote writes.
2. Check selected image sources/digests, loopback binds, mandatory independent
   keys and the private Gorse network before requests. Gorse v0.5.11's native
   `AuthFilter` logs keys on rejection. The guard rejects bad/missing keys using
   constant-time comparison and forwards only a fixed native key on a closed route
   list; never expose the native port or send a deliberate bad key to it.
3. Bootstrap native OpenPanel; apply central migration/grants; inject Galaxy
   config. Confirm actual native versions, health, authenticated empty queries,
   worker indexing and actual allowed events. An empty real business database is
   a valid empty state, not evidence that an unexecuted adapter is connected.
4. Concentrate necessary adapter and real integration checks once. Preserve first
   failures and retry only affected parts. Do not replay old page test groups or
   call a transport double a native integration. Never copy private sources into
   a demonstration event or display synthetic counts as actual business metrics.

Common observed pitfalls: Gorse's no-ranker mode rejects multiple candidate
sources; a completely internal shared network prevented expected host published
ports on the actual Docker host; OpenPanel's generated Prisma client has a custom
TS output; ingestion acknowledgement precedes ClickHouse visibility. The outbox
persists `submission_started` before sending OpenPanel, and after unknown receipt
confirms the stable event ID through the native reader rather than blindly
resending and inflating metrics. Its uncertain state survives worker lease expiry.

For the one additional native Chinese/write check, the deployment owner can run
`services/galaxy-discovery/native-probe.mjs` with a protected input file or `-`
for stdin. Input shape is `{meilisearch:{url,apiKey},gorse:{url,apiKey}}`: use the
Meili operational master key and Gorse guard key, with the actual loopback or
Docker service origins. Do not put resolved values in the command or evidence.
The script creates only one exact `galaxy_native_probe_<uuid>` Meili index and
one exact `post_<uuid>` Gorse item. The Chinese fixture is explicitly an
operational object, not Galaxy content. It waits for native Meili tasks, checks
the Chinese term match, acknowledges native Gorse item writing and reads latest
honestly. Latest may remain empty during native scheduling warm-up; it is never
called personalized inference. In `finally`, it deletes that exact Meili index
and waits for task success/404, and deletes that exact Gorse item through the
guard. It creates no Gorse user/feedback and calls no OpenPanel endpoint. A
cleanup failure leaves the exact object IDs and closed error codes for the
owner; it never issues wildcard or business-index deletion. This script is
prepared here and is not evidence of execution until the owner runs it.
