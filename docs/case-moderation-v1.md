# 一般Case的独立处理

当前补充：[验证者参与案件与双向处理 v1](verifier-participation-v1.md)已接通自愿参与、来源读取、意见和申诉；[统一审计](audit-coverage-v1.md)及既有 Evidence 重验已覆盖纠正传播。当前 Schema37/42表。下方 Schema31 和剩余项描述为原批次历史记录。

2026-09-10，本地实现，Schema31、39表。C10-06仍进行中；Official动态服务未部署。

## 行为

普通Case可以直接进入现有Moderation流程，不再要求先创建Assistance。报告人必须能读当前完整Case事件链，提交准确 `caseId / caseVersion / targetEventId` 和自己的签名Consent。来源变化要求重新查看后提交；旧报告保留原版本，准确重放不创建副本。

报告仍是指控。报告人和Case所有者是处理当事人，可以补充、纠正自己的说明和申诉；配置的独立moderator可以暂停、恢复和记录 `upheld / dismissed` 结论。Case所有者即便配置为moderator也不能裁定本人Case。Case中由所有者填写的参与者名单不等于他人的参与确认，不据此授予处理角色。当前独立性检查是报告人/所有者角色排除，不是对现实关系的认证。

所有报告、决定、申诉和更正都追加保留。`resolve`不自动解除暂停，后续需明确`resume`。文字更正不会替换既有决定；申诉后的新决定可以不同，旧决定继续保留。配置人员作出的过程决定不等于机器已经重新验证Evidence。

## 暂停与数据边界

- Case级暂停作用于关联Assistance：开放发现暂时排除、执行工作受现有暂停规则限制；参与者仍能取消和处理争议。
- Honor及依赖协作验收的参与资格沿用Assistance的当前暂停状态。独立Proof资格与Evidence重验仍需后续接通；不把关联协作暂停描述成所有Proof失效。
- 原Case事件、旧结果及CI签名事实保留，不由举报或过程决定改写。
- 举报正文只发送给配置处理人；后续决定按原规则发送给当事人。公开Case不使举报成为公开内容。
- 处理角色本身不授予Case读取权。报告详情的`source`只有在当前举报和完整Case都可见时才返回；否则为空。来源授权撤销后隐藏来源，原处理记录仍按各自Consent规则读取。
- 本人导出沿用`moderation-reports`，新增可空`case_id`；授权视图沿用既有逐条过滤。第三方报告的外键由现有删除引擎作为保留引用处理，不能为删除Case而级联删除他人的记录。

## 客户端与原生入口

仍使用`/v1/moderation/reports`和既有事件、查询、读取API。旧Assistance报告格式保留；新Case报告是严格互斥结构。`config.reportTargets`声明支持`assistance / case`，客户端不会向未声明Case支持的旧端点提交Case报告。查询可按Case或Assistance过滤，不能同时指定。

`/galaxy → 接入银河 → 查询履历 → 条目详情 → Case独立争议处理`，可选择准确来源事件、提交私有报告、查看对应处理记录。现有协作菜单的处理队列兼容两类报告；暂停标签明确Case关联工作范围。沿用原生列表、返回、准确预览、确认和本机签名流程，不更改初始化或全局安装。

## AI Agent部署与检查

先运行正常migration至31；本次只扩展既有表的目标列与索引，Case/Assistance必须恰有一种目标。API角色现有表权限覆盖新增列，无新超级权限或全局配置步骤。按当前配置加载moderatorIds，未配置时服务返回不可处理，不应宣称自动有人处理。

检查真实数据库上普通Case报告→独立决定→申诉→新决定，和旧Assistance流程；核对原文、私有导出及关联暂停恢复。以具有来源读取权的独立报告人和处理人验证，处理人不应因为角色自动看到私有来源。回退优先前向修复；有Case报告后不能直接恢复要求assistance_id非空的旧schema。
