# 冷启动、数据价值与贡献激励

[项目首页](../README.md) · [银河网络宣言](../MANIFESTO.md) · [愿景与架构](vision-and-architecture.md) · [共同治理](community-governance.md)

银河的冷启动设计同时处理三件事：使用者为什么愿意开始、真实知识怎样积累、贡献者为什么愿意留下。客户端、社区与激励机制各自承担一部分，任何一个组件都不能独自替代真实参与。

![从本地接入到共同建设的价值关系](assets/community-value.svg)

## 为什么从客户端进入已有工作

原始讨论已经提出：只有通信标准还不够，网络需要真实需求、参与者和长期资料；项目又没有现成的巨大用户入口，因此应借助已有 AI 工作环境，让有用的插件服务先进入真实工作。

| 原本的障碍 | 客户端方式怎样减少负担 |
|---|---|
| 用户要离开原工具，到一个空平台重新开始 | 在已有 AI 宿主中接入，继续原聊天和工作；需要完整讨论时再打开相应页面 |
| 先注册、填写简历，等待未来可能的价值 | 确认初始化后先在本机沿用或生成 ID，官方账户关联可跳过，经历逐步积累 |
| 用户需要反复解释已尝试的办法和环境 | 在宿主实际支持且获准的范围保留本地事实与来源，由自己的 AI 帮助整理必要背景 |
| 平台只能等人主动来发布问题 | 当用户的 AI 难以推进，或用户主动需要评审、诊断、合作时，成为寻找外部帮助的入口 |
| 一次协作结束后，经验和关系难以继续使用 | 在许可范围内保留具体参与、结果、限制和方法，方便以后的查找与合作 |

本地使用、资料上传和公开分享分别处理。客户端不是把所有工作自动交给官方的数据采集器；安装与 ID 创建也不要求先注册官方账户。当前具体路径和服务端职责见[客户端入门](client-entry.md)。

“卡住时引入外部帮助”是重要的早期切入口。后续的社区、项目与机会发现，允许用户主动找人、交流兴趣或参与创作，使用方式并不限定为反复失败之后才启动。

## 怎样逐步形成最初的供给

使用者可以先取得一次有用内容或具体帮助。愿意贡献的人可以从答疑、作品展示、小范围协作、文档、工具或适合共享的方法开始，让网络逐步形成可供后续发现的内容与联系。开放协助也为缺少历史的新参与者提供展示实际贡献的机会。

这种路径降低使用与贡献负担，仍需要有人回应、有内容可用、有真实场景支持。社区可以围绕共同主题持续交流、整理资料和帮助新人；早期运营仍需投入维护，不能用安装数、本地 ID 数或 AI 生成内容量代替实际供给。

## 什么使资料具有长期价值

| 质量维度 | 需要保留什么 | 帮助谁做什么 |
|---|---|---|
| 来源与归属 | 来自谁、哪次参与、原始出处，以及本人或外部提供的性质 | 让作者与贡献被看见，便于回到出处理解 |
| 条件与版本 | 问题、环境、适用范围、工具与方法版本、发生时间 | 判断与当前情况是否相关，理解环境变化 |
| 过程与结果 | 实际采取的办法、交付、报告结果、失败与限制 | 减少重复尝试，理解一项方法在什么情况下有用 |
| 后续使用反馈 | 引用、实际应用、部分有效、失败、再次检查或不同意见 | 看见方法后来的使用背景，逐渐修正理解 |
| 可用许可 | 可给谁看、用于什么、来源许可与当前状态 | 在允许范围内交流、组合和复用 |
| 更正与维护 | 过期、撤回、版本弃用、内容修正与来源变化 | 避免旧说明长期被当作当前结论 |

这些关系需要真实使用慢慢积累。数据多不自动等于质量高，签名或结构检查也不自动证明方法有效。参与者报告、自己的 AI 整理、外部材料和独立核查分别表述；银河提供依据，查阅者结合上下文判断。

方法沉淀与后续复用是其中一条长期价值路径。一次求助、阅读、交流或项目发现可以直接服务当前目的，不要求用户先发布 Capsule 或等待别人复用后才获得价值。

## 社区怎样鼓励持续贡献

| 机制方向 | 希望鼓励什么 | 需要怎样理解 |
|---|---|---|
| 社区交流与归属 | 答疑、作品分享、讨论、互助、引导新人和持续维护 | 普通参与有自身价值，不要求每项交流都成为正式任务 |
| 荣誉与成就 | 对明确参与、贡献或维护事实给予可见认可 | 保留事实、规则、出具者、时间和范围，多种来源分别呈现 |
| 头衔 | 让文档维护、社区帮助、适配等长期贡献容易被识别 | 属于社区角色或认可方向，不能自动变成职业资格或能力认证 |
| 积分 | 记录参与、提供反馈，并探索适合的社区激励与权益 | 取得、用途、限制与撤回等规则待设计；当前没有统一奖励或兑换制度 |
| 等级 | 形成持续参与的进展感与归属，服务适合的社区条件 | 社区参与等级与专业资格分开；不推出统一的可信度总分 |
| 合作与生态支持 | 让贡献者获得使用反馈、合作、维护工作及未来资助机会 | 实际合作由当事人约定，资助需先形成组织、经费与公开规则 |

原始设计中的荣誉、排行榜和等级重视社区凝聚。后续边界已明确：银河不自行判断可信度，不把荣誉或资料数量换算成通用可靠性排名。因此，旧方案中的专业排名、付费资格等提议不能不加区分地作为今天的全站规则。

内容受众可以按创作者有权设置的范围包含账户、等级或成就等条件，具体规则仍需细化；这不等于所有知识都要按统一等级逐级解锁。作者也不能通过一项发布扩大他人内容、回复或附件的许可。

## 当前基础与继续建设

| 范围 | 当前可据以说明的基础 | 本次保留的发展方向 |
|---|---|---|
| 低负担接入 | 本地 ID、AI 宿主接入、所选资料范围，OpenCode 的本地工作记录路径 | 更多宿主中的自然接续与真实长期使用 |
| 社区与实际协作 | 公开内容、讨论、项目、请求、参与和结果等实现基础 | 真实内容供给、响应质量、持续关系与社区运营 |
| 有限贡献认可 | 荣誉规则版本、相应来源查询和贡献认可界面基础 | 头衔、积分、等级与完整激励规则继续设计，不据此宣称整套系统已经交付 |
| 知识的继续使用 | Capsule 版本、来源许可、应用与结果报告基础 | 多场景真实使用、失败反馈和长期维护 |
| 公共组织与资助 | 本轮明确提出共同治理和生态支持方向 | 基金会／理事会的组织形式、规则和经费尚待确定 |

最新阶段见[当前状态](status.md)，参与收益与官方服务方向见[商业说明](business-and-participation.md)。本页不新增积分数值、固定奖励、收费等级或资助额度。

## 整理依据

本页回查早期“标准仍需真实参与和现有工作流入口”的用户讨论、社区等级与凝聚的原始表述、Core v3.1 的本地先行与开放协助章节，并按 2026-10 的可信度判断边界、创作者受众选择及本地积累决定修正旧设计。头衔、积分和共同治理结合本轮用户补充作为发展方向记录；当前实现核对了本地准备、荣誉规则与贡献认可等相关代码，没有把历史设想全部当成已发行机制。
