# Hub、银河官方与信息传递

[项目首页](../README.md) · [愿景与架构](vision-and-architecture.md) · [参与价值与商业方向](business-and-participation.md) · [技术核对说明](technical-faq.md)

Hub 的原始定位是“自己的共同基础、自己的规则和自己的事实网络”。企业、专业社区、行业联盟或服务提供者可以围绕自己的成员与重复需求经营本地网络，再选择与更大网络互通。

官方与第三方的关系同时包含独立运行、选择性发现和受控交换。**连接可以增加发现与协作机会，不应变成无条件交出原始资料或依附官方的要求。**

下图表达设计角色。当前已有有限直连实现；完整公共索引、独立运营生态和可选 Relay 的成熟程度另列说明。

![Hub、官方网络与可选服务的关系](assets/hub-topology.svg)

## 四种角色分别做什么

| 角色 | 目标与职责 | 与其他角色的关系 |
|---|---|---|
| 官方公共网络 | 提供公共发现、基础内容与交流、来源和状态查询，以及实际开放的信息服务 | 希望成为有用的公共入口；不是唯一合法索引，也不是所有身份和 Hub 的强制根或中转 |
| 官方参考 Hub | 官方作为普通运营者，在一个具体场景中验证产品、成员价值和协议兼容性 | 是参考运行角色，不等于整个银河网络；不因官方身份取得第三方没有的隐藏字段或特殊互通权 |
| 第三方 Hub | 自主运营成员、内容、专业能力、服务、数据政策和商业规则 | 可以本地运行，选择官方服务、与其他 Hub 直连，或连接其他合适的外部系统 |
| 可选 Relay | 在确有传递、离线或可靠性需求时，提供双方选择的转发服务 | 属于设计中的可选服务；当前有限直连 profile 没有启用 Relay，不把转发权当作原文阅读权 |

官方参考 Hub 与第三方 Hub 共享协议语义，实际服务仍可能有各自支持范围。代码开放、普通网站账户、Hub 成员身份、长期主体和每次资料授权是不同事项。

## 信息流一：Hub 内部运行

1. 成员在该 Hub 的服务、自己的客户端或已授权的外部系统中交流和工作。
2. 本地环境或 Hub 按实际选择保存内容、来源、过程、结果与必要版本。
3. Hub 的成员政策、数据保留和访问规则约束本地使用。
4. 是否对外公开、分享摘要、开放某份证明或完全不对外提供，由相应权利人和有效规则决定。

这条路径的设计目标不要求使用官方公共网络。当前独立部署包、运维配套和实际独立运营验收仍需逐项完成；“架构允许自治”不等于已经交付任意环境一键自建。

## 信息流二：选择性进入官方或其他发现入口

设计中的公共发现路径是：

```text
来源 Hub／本人选择可分享的内容和范围
  → 公开元数据、获准摘要、证明或来源引用
  → 官方或第三方索引按其服务范围组织发现
  → 查阅者取得可见线索和来源位置
  → 需要进一步材料或参与时，再向来源方接续相应权限与联系
```

可能的公开内容包括服务或 Hub 的范围、声明版本、联系意愿、方法介绍，以及获准公开的参与资料。证明应保留出具者、对象、时间、适用范围与当前状态。它们不附带来源 Hub 的全部工作、聊天和文件。

索引负责让人找到线索，来源服务负责决定当前实际能读取什么。看见索引结果不自动成为对方成员，不取得私聊或工作正文，也不代表对方已经接受合作。索引和通知应尊重来源更正、到期和撤回，不能把旧缓存当成持续许可。

**这是一条开放网络的目标路径。** 现有网站发现、Hub 声明及部分来源交换并不等于完整跨网公共索引已经成熟上线。具体可交换内容应以当前服务与协议为准。

## 信息流三：Hub A 与 Hub B 直接查询

当前实现中的 `galaxy-direct-proof/1` 是两方、有限范围的直接交换：

1. 双方运营者明确选择对端服务地址、公钥、Hub、协议版本、允许来源、用途、频率、分页及有效期；本地记录不代替对端实际批准。
2. 相应来源主体另外授权具体资料及版本／哈希，限定可以查询的主体和到期时间。
3. A 发出签名查询。查询会向 B 传递请求主体、双方 Hub 与服务地址、协议标识、用途、分页或回查范围等必要信息，并非匿名请求；原始问题或任务正文不因查询自动发送。
4. B 检查当前协议、成员及来源授权，返回允许的具体证明或选定贡献字段，保留原来源、报告性质和有效期。
5. A 检查响应签名、接收对象、请求关系、协议哈希、用途与期限，并按相应规则检查原证明。对端的报告仍是对端有范围的声明，不变成 A 或银河官方新作出的能力认证。
6. 后续需要联系、加入对方空间、读取更多内容或执行工作时，再使用对方实际支持的业务入口和许可。

| 信息类别 | 当前有限直连是否传递 |
|---|---|
| 双方 Hub、请求者、协议、用途与分页／回查信息 | 作为相应请求范围传递 |
| 选定的 CI 观察证明 | 在双方协议和精确来源授权允许时传递，保留出具者与签名 |
| 选定的贡献摘要字段 | 可以传递事件类型、参与主体，以及被选择的角色、报告结果、时间等非叙述字段 |
| 来源状态、有效期、不可用状态 | 按当前查询结果传递 |
| 私人任务上下文、整段聊天、项目文件或全部本地历史 | 不属于此 profile 的自动交换范围 |
| 模型控制、自动接单、付款或进一步业务权限 | 不由这次只读资料查询授予 |

当前 profile 的来源类型限于 `ci-proof-v2` 和 `contribution-summary`，不是任意资料与全部协议对象的通用复制机制。约定不持久保留响应正文，不等于系统完全不保存协议、授权或操作状态等必要元数据。

## 信息流四：Bridge 与外部系统

Bridge 把获准的外部事件或资料映射进银河可理解的结构，说明源系统、源对象、目标对象、映射版本、去重、撤回和出处。例如一个 CI 观察可以带来某次执行的有限事实，不能因此证明作者的全部能力。

原始设想希望现有平台无需整体迁移就能参与。实际接入要遵守来源系统的 API、许可和访问条件；Galaxy-compatible 不会替外部系统授予资料导出权。

## 可选 Relay 与收费关系

直连是独立路径。使用双方自己的网络和服务、没有调用官方增值服务时，设计原则是 **不产生强制官方协议费**；当前有限交换也把官方协议费固定为零。这不等于第三方 Hub 无运行成本，也不约束第三方自己向成员收取其已说明的服务费用。

官方可以在实际提供更广发现、高频 API、托管、维护支持或将来的 Relay 等服务时，按用户或 Hub 选择的服务条件收费。Relay 的传递权限、保留和日志规则应单独说明；转发不能修改原来源、把送达当成任务成功，或自动取得原文和训练权。

可选 Relay、完整托管 Hub 及具体收费套餐仍是需进一步落实的服务方向。本页不发布价格、分成比例或服务时限。商业边界见[参与价值与商业方向](business-and-participation.md)。

## 变更、撤回与退出

协议到期、对端退出、来源撤回、成员关系变化或版本不再适用时，后续查询按当前状态处理。已记录一次发送或收到响应，不代表以后永远有权读正文。

主体和来源可以在获准范围内携带，原出具者、签名、声明范围和当前状态继续保留；携带不等于接收方独立复核，也不自动合并账户、组织和所有权限。退出、导出和删除作用于实际受控的位置，不能承诺已经传出的所有副本都被远程抹除。

## 已有基础与仍需验证的部分

| 已有实现基础 | 仍属于设计或待验证的范围 |
|---|---|
| Hub 声明、章程、有限成员范围、来源授权、直接签名交换与当前状态检查 | 多个真实独立运营者的长期互通、完整自建交付和生态供给 |
| `galaxy-direct-proof/1` 的有限证明与贡献字段查询 | 面向任意资料的通用联邦、完整全网公共索引、跨站聊天室联邦 |
| 来源、版本、许可、退出与撤回的相应处理 | 设计中的可选 Relay、全面托管和具有保证的商业套餐 |

Prosody / XMPP 承担相应聊天室通信和存储接入；它与这里的 HTTPS Hub 交换不是同一条传递路径。详见[技术核对说明](technical-faq.md)。
