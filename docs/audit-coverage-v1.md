# 统一审计覆盖与当前边界

2026-09-10，C16-01/02本地实现；数据库Schema37，失败队列SQLite格式2。原任务的人工、运营及发布验收仍保留，动态云服务未部署。

## 字段与来源

|字段|含义|
|---|---|
|actor / client_id / audience|执行主体或明确标注的后台组件、客户端/组件、服务端点|
|action / object_id|固定动作与对象标识；HTTP失败使用固定路由模板，不保存原始路径|
|scope / consent_id|操作所需权限与具体业务Consent；认证、通知偏好等无业务Consent的操作明确为空|
|binding_id / binding_scopes|业务授权关联的绑定及范围；不能当作当前仍有效|
|caller_binding_id / caller_client_id / caller_audience / caller_binding_scopes|实际调用方的绑定、客户端、受众与绑定范围|
|credential_scopes|本次凭据范围，与绑定授予范围分开|
|request_id / http_request_id / idempotency_key|原接口关联键、真实HTTP请求号（如有）和业务去重键|
|created_at / outcome / context_version|登记/捕获时间、结果，以及是否采集完整主体业务上下文|

主体业务成功事实与审计在同一事务提交。scope和credential_scopes使用重新核验的数据库授权快照，不接受调用方额外传入的伪造范围。后台任务、失败请求或历史记录不能伪装成完整业务授权，继续用context_version=0或对应后台事件的明确来源规则。NULL表示不适用或未采集，须按事件类型解释，不填造Consent或用户凭据。

## 已接通的路径

|业务路径|审计与关联|
|---|---|
|身份绑定、撤销、会话建立|绑定/挑战/新会话及实际调用范围；认证本身不生成业务Consent|
|Case、Consent、Evidence提交、Proof、Assistance、Context、Capsule、Builder|事件及其Consent、调用方和幂等键；复用原有事务审计|
|Profile自述发布|profile.publish关联声明ID、发布Consent、history scope与调用快照；重复提交保留一条记录，不记录自述正文|
|通知偏好与已读状态|notification.preferences用主体及偏好revision关联，notification.read用来源类型及事件ID关联；已读重复调用不重复记录状态改变|
|材料正文、元数据、列表和授权视图导出|每次成功访问追加独立读取记录，仍逐次校验实时权限；材料正文不进入日志|
|Evidence观察、重试耗尽及不可用修复|验证任务、尝试次数与Evidence/Consent；后台组件不冒充用户凭据|
|业务争议与处理命令|报告、补充、申诉、处理决定及独立重验事件，原事件保持不可改写|
|本人/经审批的审计读取与导出|独立限时审批、读取摘要、范围与操作者；读取审计本身留痕|
|本人数据导出、治理配置、事故通知和恢复操作|沿用相应操作记录；治理配置的申请、独立审核、实际加载及角色差异可关联|
|HTTP拒绝、内部错误、解析器错误和中断|有界持久队列、重启重放、请求/action去重；认证通过后保存当时的公开权限快照|

通知偏好仅改变本人站内通知，不构成新的材料披露授权；不额外制造Consent。Schema37只增加这两种通知动作的无Consent完整审计约束，无新表或数据库角色权限。

HTTP失败发生在认证通过之后时，scope、凭据范围和调用绑定元数据在认证返回时捕获。数据库故障、后续撤销或安装ID变化不会使延迟补写使用新的绑定信息替代原快照。未通过认证、旧队列项或直接兼容调用缺少快照时保留部分上下文。失败日志仍不证明业务已获准、事务没有提交，或调用者现在仍可访问。

## 一条证据纠正的追踪

沿用既有独立重验流程：处理人签署revalidate事件，jobs保存该事件、报告和Consent ID；Worker观察审计通过job ID及attempt关联，新增Proof通过新observationId关联。自动化用同一原CI来源从success重验为failure，覆盖：

- 重验排队后，旧Proof不再被当前读API认可；Profile去掉该有效Proof，依赖它的Honor变为证据不足，搜索不继续返回旧成功记录。
- 新失败观察可以发布新的受限CI事实Proof；Profile和搜索显示新事实，成功过滤和要求成功的资格/Honor不会恢复。
- 决定、申诉、观察与旧签名均保留，不通过改写历史制造新的结果；审计能从处理命令追踪到验证任务和新Proof。

原始来源为隔离合成数据，不作为真实外部验证者或个人能力的证明。正式来源和真实用户验收按原计划执行。

## AI Agent部署与恢复

1. 按当前锁文件安装，并用迁移角色升级到Schema37。API/Worker角色文件无新增权限；在开始服务前核对源码与迁移版本一致。
2. 失败队列保持在显式trust目录的持久卷。格式2兼容读取格式1旧项并保留其NULL语义，首次打开升级格式号。旧程序不能接管格式2队列；回退使用兼容版本或已验证的整体恢复，保留队列和WAL，不删积压项。
3. 启动后确认队列ready、补写进度和错误状态。业务成功事务审计、失败队列交付和后台操作分别核对，不以单一绿色状态代替全部覆盖。
4. 真实运营人员、独立密钥保管、异地归档目的地及其保留策略仍待落实。已提供的配置归档、备份和恢复代码不等于已部署的归档系统。

API/Worker角色不可任意改写或删除审计；数据库所有者和主机管理员仍可能绕过应用角色。治理审核与记录不能被宣传为绝对防篡改。恢复隔离等没有主体会话的维护事件保留组件来源，未知端点/授权字段不回填；目标环境复验继续由C18/C01记录。
