# Honor 规则版本与历史 v1

2026-09-10，本地实现。对应 C13-01；Schema 38 / 43 张表。动态服务未部署。原始任务和验收条件见[完整开发清单](../../../GALAXY_OFFICIAL_BASIC_CLOUD_DEVELOPMENT_CHECKLIST_v0.1.md) C13；本次补齐规则历史，不改变两类贡献规则的业务含义。

## 已实现行为

`honor_rule_versions` 按 endpoint、规则 ID、版本保存完整规则定义，关联首次运行配置事件。API 启动时将本次实际加载的规则、启用引用和审计记录放在同一事务中；任一旧版本定义冲突，整次配置记录回滚，启动失败。

同一版本不能改变成员、关联组、领域、社区、条件、仓库、时间窗或排名门槛。定义使用已有 `canonicalize` 库生成 JCS 字节并计算 SHA-256；成员和关联组按集合顺序归一，GitHub 仓库名称按现有匹配语义忽略大小写。更换顺序不会被误认成另一套规则。

`revoked` 是运行状态，不改变规则定义摘要。配置可撤销某版本、移除某版本或重新启用完全相同的定义；每次启动的当前引用留在既有 `runtime_config_events`。移除后仍能查到旧定义和最后一次撤销标记，当前状态显示 `configured=false`。这表示规则历史，不证明某人过去曾经获得荣誉。

实际 API 使用数据库中的最新配置观察，已经运行的 Honor 服务在下一次读取时使用新规则状态。原卡片 ID 保持稳定；撤销、移除、到期会使旧卡片失效，来源贡献记录保留。新版本按自己的门槛重新计算，不继承旧版本资格。运行配置中的相同定义重新启用后，符合当前授权来源的卡片可恢复有效。

## 读取入口

| 入口 | 行为 |
|---|---|
| `POST /v1/honor/rules` | 当前配置规则；返回 `ruleHistorySupported=true` |
| `POST /v1/honor/rule-history` | 可按 `ruleId` 查询版本，`after` 游标、`limit` 1–20；默认 8 条 |
| `POST /v1/honor/query` | 原查询兼容；旧版本可查询当前卡片，包含 registry 引用 |
| `GET /v1/honor/{subjectId}/{ruleId}/{ruleVersion}` | 原状态链接兼容，按访问者当前权限重算 |

历史接口返回每个规则版本、公开定义、首次配置 ID、定义摘要、当前配置 ID、当前启用/撤销状态。`nextAfter=null` 表示该次查询无下一页。列表以持久化序号排序；分页之间配置可能变化，每页均带自己的配置 ID。完整启用、撤销、移除的配置事件沿革复用运营配置审计导出。

成员和关联组名单仅存在私有运营定义中，公开历史不返回这些字段。摘要用于关联服务保存的完整定义，公开响应因省略私有字段不能独立重算该摘要。响应不是独立签发的能力证书。

便携客户端 `@galaxy/client/honor` 增加 `ruleHistory`，宿主控制器增加 `honorRuleHistory`；历史读取为匿名公开请求，不携带身份或会话凭据。原生 Honor 菜单可查单条或全部历史规则、分页、打开旧版本当前卡片。当前规则列表为空时历史入口仍保留。首次 `/galaxy` 初始化交互未修改。

## AI Agent 配置与部署接线

1. 使用现有迁移入口升级到 Schema 38，再应用 `api-role.sql`。API 对新表只有 SELECT/INSERT；Worker 无需新增权限。旧版 Schema 37 服务不兼容新 Schema，应按现有备份恢复或前向修复流程处理回退。
2. 在已选环境的 `GALAXY_GOVERNANCE_CONFIG` 中配置最多 8 条当前规则。省略时是空规则集；生产试点继续使用既有治理配置审核流程，测试中的合成成员和规则不直接用作运营政策。
3. 原启动路径完成 `recordRuntimeConfig(..., honorRules)` 后启用 `services.honor.useRegistry()`，然后启动监听。自建嵌入服务也须完成这两步。仅调用 `new HonorService(..., rules)` 保留原内存模式兼容，`ruleHistorySupported=false`，不能声称有持久历史。
4. 检查公开规则、历史分页、旧版本状态及配置事件。历史路由已接入既有 Caddy 允许清单、公开元数据额度、HTTP 失败审计和停服期间的只读入口。
5. 变更规则内容必须增加版本；撤销或移除无需删除历史定义。没有自动发放积分或能力认证的操作。

新表随 PostgreSQL 数据备份保存；本轮未执行生产备份恢复或云端迁移。规则是包含多主体引用的运营配置，未纳入本人所有数据的 31 个导出集合。本人数据删除会保留规则定义，并在执行回执 `operatorPolicies` 中报告仍含本人 ID 的规则版本数量，明确 `cleanupImplemented=false`。运营政策的保留和最小化仍需 C00/C18 的生产政策处理，不能宣称全部个人引用已清除。
