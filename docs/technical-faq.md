核对日期：**2026-10-21**。本页回答公开概览没有展开的技术问题：Capsule 保存什么，效果怎样记录，哪些上下文会离开本机，权限如何撤回，以及 Hub 和 XMPP 的关系。

## 0. 初次接入是否需要先搭建服务或注册官方账户

普通客户端在已有 AI 宿主中通过插件或 Skill＋MCP 接入，AI 可以协助完成环境发现、安装和本机初始化。程序在本机沿用或生成银河 ID，可以跳过官方在线账户注册和关联；Keycloak、PostgreSQL、Prosody 等由相应 Hub／官方服务维护者部署；客户端聊天经银河 HTTPS 业务接口使用，不直接配置 XMPP 连接或单独注册 XMPP 账户。

当前实现中 `galaxy_native_initialize_preview` 和 `galaxy_native_initialize` 负责本机准备，`galaxy_native_connect` 另行连接所选服务；ID 在 Hub 的接入与在线账户注册不是同一个动作。OpenCode 的 `setup.mjs` 已将本机准备接到同次安装选择，其他宿主按其插件或 MCP／Skill 能力初始化。当前安装工具仍读取所选官网的公开配置，Node.js 22.13+ 也是 0.1.16 的真实运行要求；不据此宣称完整安装完全离线或任何宿主都能一键完成。

详细使用路径、账户分工与实现在[客户端入门](client-entry.md)。一次求助、找到相关内容或参与交流就可以产生当前价值，Capsule 发布和他人复用是后续可选积累，不是使用网络前必须完成的闭环。

## 1. Capsule 中到底保存什么

当前实现有明确的 Capsule v2 结构。它保存方法内容、精确来源、许可和版本等资料；实际使用情况另以使用记录保存。

| 字段 | 含义 |
|---|---|
| `schemaVersion`、`kind` | 本页对应 v2 的 `version` 事件；兼容历史 v1 不表示两者可以混算 |
| `id`、`capsuleId`、`version`、`expectedRevision` | 本次版本事件、所属 Capsule、方法版本及写入时预期的修订号 |
| `title`、`problemPattern` | 方法名称与要处理的问题模式 |
| `environment` | 环境名称与版本 |
| `solutionStrategy` | 方法或步骤正文 |
| `tools`、`skills`、`mcpRefs` | 使用的工具、Skill 与 MCP 引用 |
| `verificationMethod`、`limitations` | 建议的核验方法与明确限制；填写这些内容不等于核验已经执行 |
| `capabilityId`、`applicableScope` | 分类标识与适用范围；不是能力认证 |
| `license`、`contributors` | 发布者声明的许可和贡献主体；贡献者列表本身不代表共同作者已同意 |
| `sourceResolution` | 来源工作的 `caseId`、结果 `resultId` 与 `resultVersion`，以及关联证明和核验引用 |
| `sourceRefs` | 选定的来源及其版本，例如尝试、介入、结果、证据、核验、配置、选定消息或成果材料 |
| `permissionRefs`、`attributionRefs` | 精确来源许可与归属引用 |
| `publicationClass`、`synthetic` | 本路径的发布类别为 `formal-source-success`；是否为合成或测试来源单独标记 |
| `externalReferences` | 外部链接及许可说明；该字段限定为链接引用，不导入外站正文 |
| `redactionConfirmed` | 发布材料的脱敏确认声明；声明本身不能证明所有敏感信息已被识别 |

[Capsule v2 JSON 示例](../examples/capsule-v2.json)符合当前字段结构，全部标识与内容均为合成示例。示例没有真实来源或许可，不能据此向服务提交真实发布，也不代表一次成功复用。

### 效果由谁回写

实际使用者在另一个工作中提交使用记录。记录分成三种：

| `kind` | 记录什么 |
|---|---|
| `reference` | 在指定工作中引用某个方法版本；不宣称已经实际应用 |
| `apply` | 实际采用的部分、环境与环境差异、精确的尝试或介入来源、对应结果，以及使用说明 |
| `reverify` | 针对原应用和同一结果版本补充核验记录，保留原应用引用 |

`apply` 和 `reverify` 的 `outcome` 为 `succeeded`、`partial`、`failed`、`inconclusive` 或 `conflicting`。服务核对它与所引用结果的 `reportedOutcome` 一致，并核对行为主体、来源版本、环境、工作及参与范围。Native 准备流程从当前可读的结果取得相应状态，不只接受一段任意的“我成功了”文本。

这仍然是**有来源约束的参与者结果报告**。程序检查记录是否自洽、是否获得授权，不据此独立证明方法与结果之间的因果关系。当前接口明确保留 `verifiedReuse: false`、`capabilityVerified: false`；独立验证复用数不会因提交报告自动增加。

正式方法发布路径要求引用当前可读、报告结果为成功的来源。这个要求不表示平台已经独立判定该成功真实有效。来源被更正、许可撤回、版本弃用或存在安全问题时，当前读取和新应用资格会重新判断。

### 谁能读取、发布和复用

方法发布及使用记录按其 Consent 中的可见范围和接收对象处理。可读取某个工作或聊天室，不自动取得把他人内容发布成方法的许可。

涉及他人来源时，许可明确记录选定来源及版本、被授权主体、许可名称、用途范围、归属、是否允许公开及可选到期时间。使用覆盖性许可作为依据时，还要提供相应许可出处。服务核对来源作者、授权对象、许可一致性和公开范围。

自己的确切来源可以由本次发布授权覆盖，他人的来源需要相应许可。声明许可不等于平台独立裁定其法律归属或许可兼容性；使用者仍需按所声明的许可和实际权利范围使用内容。

许可可以由相应主体撤回。后续服务读取、发布和应用会检查当前许可与来源状态。撤回控制未来服务访问，不能保证已经合法取得或已被他人保存的外部副本从所有设备消失。

## 2. 客户端数据怎样流动

客户端的本地工作记录、自己的模型整理、可选的本人线上副本与主动发布分别处理。

```text
宿主提供的事件和获准上下文
  → 本机记录：来源、有限内容、工具状态与环境
  → 用户自己的模型可整理摘要，保留模型整理与观察事实的区别
  → 按上传档位投影字段
  → 检查选定账户、工作／会话范围与当前授权
  → 发送允许的资料，保留原操作及结果状态

发布请求、帖子、方法或向他人发消息
  → 使用对应业务动作、接收对象与授权范围，另行处理
```

OpenCode 的自动采集依赖其公开事件接口。其他宿主的事件、读取和界面能力不同，不能据此声称相同范围已经自动采集。自己的宿主给模型发送什么，仍由宿主和该模型服务的配置管理；银河的上传档位限制的是银河自己的资料上传。

### 四档上传范围

| 档位 | 可以进入银河上传投影的资料 | 继续排除或需要单独选择 |
|---|---|---|
| `local-only`，仅本地 | 不上传本地工作资料 | 业务查询、主动发帖等按各自业务权限处理 |
| `history-overview`，履历概况，初始默认 | 工作与主体标识、宿主与符合格式的会话来源标识、工作类型、角色、时间、结果状态与来源类型、主要模型工具和环境版本 | 不含工作标题、自由摘要、过程观察、路径或原会话正文；来源标识仍可能关联具体活动，不能称为匿名数据 |
| `work-content`，选定工作内容 | 另允许所选工作的标题、说明、摘要与获准观察／材料 | 不自动包含所有项目文件或完整会话 |
| `conversation-archive`，可选会话归档 | 工作范围同上；另行启用完整会话并明确选择会话后，才允许该会话实际保存的消息 | 只升档不能启用全部会话或回填全部旧内容 |

档位只确定允许的数据类别。实际同步还要有选定服务、目标账户和工作或会话范围；初始默认第二档不会自行建立这些选择或开始上传。是否同步后续工作、是否包含既有材料，也属于实际选择。

工作详细内容采用有界窗口：当前实现对单次工作投影设定大小与观察条数限制，并保留包含条数、序号范围和是否缺少早期内容等覆盖信息。完整会话使用单独的选定归档流程，不会藏在概况摘要中上传。

### 脱敏在哪一侧做

本机记录流程会对可识别凭据字段和常见凭据文本进行排除，保留排除位置和类别；上传投影还会检查凭据。服务端工作资料输入也有严格字段结构、大小、覆盖范围与凭据检查。

第二档通过程序白名单投影字段，不是让模型把正文改写成一段“看起来安全”的摘要。第三、四档可能包含实际正文和选定内容；凭据排除不等于全面匿名化，也不保证识别所有个人信息、客户资料或商业秘密。需要根据实际内容和共享目的选择范围。

这些检查说明的是已核对的工作资料路径，不能外推为所有业务接口、每种附件及所有第三方宿主都经过同一套完整脱敏。

## 3. MCP 工具与授权、撤回

以下是本次在公开 **0.1.16 发行代码**中能定位到的相关工具名称。它们是有代表性的接口清单；宿主实际通告的工具、可用权限和执行结果，仍以当前环境的 `tools/list` 及调用为准。

| 用途 | 相关工具 |
|---|---|
| 查询账户开放资料 | `galaxy_account_public_by_id`、`galaxy_account_public_profile`、`galaxy_account_public_ids`、`galaxy_account_public_credentials` |
| 本地工作阅读与导出 | `galaxy_local_work_list`、`galaxy_local_work_get`、`galaxy_local_work_export` |
| 自己的模型保存本地整理 | `galaxy_local_work_pending`、`galaxy_local_work_summary`、`galaxy_local_work_note` |
| 上传档位和上传前预览 | `galaxy_local_upload_privacy_get`、`galaxy_local_upload_privacy_set`、`galaxy_local_work_upload_preview` |
| 选定工作同步 | `galaxy_work_sync_settings`、`galaxy_work_sync_choice`、`galaxy_work_sync_flush` |
| 本地完整会话与选定归档 | `galaxy_local_archive_settings`、`galaxy_local_archive_configure`、`galaxy_local_archive_export`、`galaxy_archive_sync_choice` |
| 删除相应副本 | `galaxy_local_work_delete`、`galaxy_local_archive_delete`、`galaxy_work_cloud_delete`、`galaxy_archive_cloud_delete` |
| Capsule 准备、执行和核对 | `galaxy_capsule_work_sources`、`galaxy_capsule_work_read`、`galaxy_capsule_work_prepare`、`galaxy_capsule_work_execute`、`galaxy_capsule_work_status` |
| 房间 Agent 权限 | `galaxy_chat_agent_grant`、`galaxy_chat_agent_revoke` |

读取、准备和正式发布是不同动作。Capsule 的 prepare 会在本地保留准备状态，**也会把方法 payload 发给所选服务作预览和来源检查**；这一步不创建正式发布或使用记录，服务返回的草稿存储范围是用户侧。因而“尚未发布”不能解释成“完全没有网络传输”，预览也需要在允许向该服务提供所选内容的范围内进行。execute 沿 Native 的实际选择与授权流程执行正式业务，不能因为模型给参数写上 `confirmed` 就推定获得了人的新授权。

授权会限定服务、身份、业务动作、对象、资料内容及可见范围等上下文。已经明确授予且仍有效的范围可以沿用；新披露或扩大范围需要实际选择。服务会核对当前控制、有效权限和相应来源，原操作结果未知时先核对原操作，避免以重发新内容替代恢复。

可以停用选定同步、降低上传范围、撤回对应来源许可或房间 Agent 权限；设备和服务绑定由其自身控制流程处理。撤回未来服务访问不表示外部模型进程已经被终止，后者需要宿主确认。停用上传也不自动删除已上传副本。

## 4. 可见范围、导出与删除

| 位置或资料 | 已核对的控制范围 | 不应推定的结果 |
|---|---|---|
| 本地工作记录 | 按当前身份阅读、导出实际保留的观察与摘要，删除选定工作并清理相应待上传正文 | 不等于导出完整聊天，也不删除宿主原记录或线上独立副本 |
| 本地会话归档 | 按选定宿主与会话捕获、分页导出、删除及配置清理 | 不补造未捕获的早期消息；不自动删除宿主原会话 |
| 本人线上工作与会话 | 按选定账户管理私有副本、导出实际保存的内容、删除及使用相应清理设置 | 账户公开查询开关不会自动公开这些私有副本 |
| 线上删除后的同步 | 同一来源范围保留删除状态，普通重试或保存未变设置不会自动恢复；恢复需要明确重选相应来源 | 不能把本地原件仍存在视为允许自动重建线上副本 |
| Capsule、帖子、请求等发布资料 | 按各自可见范围、许可、当前状态与生命周期处理 | 一项副本删除不能代表全网已收回所有已传播内容 |

来源主体、署名与许可记录提供控制和解释依据，不自动裁定法律上的所有权。导出的是当前有权取得且实际保存的资料；删除也按具体位置和对象范围报告。这里没有承诺对所有公开业务对象、备份介质和第三方副本提供同一种立即彻底删除能力。

## 5. Hub 如何互联，XMPP 承担什么

当前有两方有限范围的直接互联实现，其协议标识为 `galaxy-direct-proof/1`。它不是完整的全网资料复制协议。

| 项目 | 当前机制与边界 |
|---|---|
| 参与方 | 双方 HTTPS 服务地址、Hub 与运营者标识、明确选择的服务公钥和有效期 |
| 协议范围 | 双方批准的协议版本、来源种类、发现帮助目的、速率、分页、响应有效期和退出状态 |
| 允许来源 | 选定的 `ci-proof-v2` 或 `contribution-summary`；后者只含选择的非叙述字段，例如事件类型、参与主体、角色、报告结果与时间 |
| 来源许可 | 具体来源及版本／哈希、指定请求者、用途和到期时间；许可可撤回，查询时重查 |
| 传输与检查 | 直接 HTTPS 请求，核对签名封套、协议哈希、发送与接收端、请求者、用途和有效期；相应证明保留原出具者及签名检查 |
| 数据边界 | 不夹带原任务上下文；当前约定不留存响应正文，不经官方中继；外部来源也不因此成为新的独立证据或能力认证 |

主体身份、账户、Hub 成员关系和跨 Hub 许可分别检查。加入一个 Hub 不会自动取得其他成员全部资料，也不会因为双方互联就合并原有主体或权限。

Bridge 描述外部系统的来源对象、目标对象、映射规则、授权、去重、撤回和出处。映射或一份声明并不证明第三方系统已经独立运行；来源观察和作者陈述仍保留各自含义。

**Prosody / XMPP 是 Hub／官方服务端内部的聊天基础设施。普通银河客户端通过 HTTPS 调用银河聊天业务接口，无需安装 Prosody、配置 XMPP 服务器或单独注册 XMPP 账户。** 已核对的适配器在 Hub 服务器侧运行，只连接该服务器的私有回环地址，配合房间与归档能力处理消息。上述 Hub 互联通过 HTTPS 和有限签名交换完成；不能因为采用 XMPP 就声称已经实现跨站聊天室联邦、全局身份互信或完整离线企业网络。

Hub、Bridge 和有限互联有具体实现基础，多独立运营者、企业完整环境和长期互通效果仍需要实际部署及使用验证。

关于官方公共网络、参考 Hub、第三方独立经营、可选索引和 Relay 的完整角色关系，以及查询、来源授权和后续协作的分步信息流，另见 [Hub 与官方的运作](ecosystem-and-hubs.md)。
