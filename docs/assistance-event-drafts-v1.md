# 协作事件草稿 v1

2026-09-10 本地实现。求助/赏金草稿之后，原生宿主现在也保存后续协作事件的填写进度，动态服务仍未部署。

## 使用流程

从协作详情选择申请、邀请、候选选择、确认参与、范围变更、交付、验收、取消、到期、争议、解决方案或请求者反馈，会创建与该请求关联的本地事件草稿。已确认的字段、申请报价、资格证据引用和步骤游标保留；未确认的输入不保存。

“协作请求 → 本地草稿与提交恢复”可恢复这些草稿；未连接时也可通过“服务信息 → 本地协作草稿”继续填写。离线入口不读取服务、不签名、不提交。恢复申请不会自动申请，选择草稿不会自动成交，范围变更仍需另一方确认。

所有既有 Assistance 事件类型沿用原 Schema 和服务端状态机。邀请及反馈限制仍由原业务规则执行；交付仍需绑定真实 Case 的 Attempt/Evidence，草稿文本不是已发生的协作事实。

## 版本与目标

事件草稿保留最小来源摘要：协作 ID/版本、请求标题、当前角色及状态、已选参与者、已确认/待确认范围、招募期限与资格政策。它不包含其他申请人的正文或 Context。

在线恢复或准备提交时读取当前协作：
- 版本相同：继续填写或进入准确提交预览。
- 版本变化：展示原/当前版本、状态、已选参与者和范围。只有明确选择“按当前版本继续编辑”才更新草稿来源；已填文本保留，并重新经过提交预览。
- 参与角色改变、原申请撤回、交付或解决方案目标已替换：保留本地内容，要求回到当前协作重新选择目标。
- 协作被暂停：除取消外，不准备其他操作。

刷新版本不会替换 offerId、offerIds、deliveryId 或 proposalId。普通字段保存不能更改来源或目标。准备提交时再核对草稿修订和当前服务版本，防止刷新之后又发生变化。

## 提交与恢复

准备后的事件 ID 等于草稿 ID，载荷从存储中的准确字段生成；草稿、原 payload 和 Consent 一起冻结。之后复用[提交恢复日志](assistance-recovery-v1.md)：回执丢失或断网先核对原事件，再按原 ID、版本和正文重试。

新绑定可重新确认同一披露范围，不能借重启换目标、换版本或延长请求期限。事件进入提交日志后不再编辑；重新选择业务操作会形成新的草稿。服务端仍负责最终的角色、期限、参与人、引用和状态检查。

## 实现和剩余工作

复用 assistanceDrafts、assistanceOperations 和既有 Core 写锁。原请求草稿与已有提交日志直接兼容；数据库仍为 Schema35/42表，无迁移或新接口。本次客户端发布入口和既有独立客户端源码未改变。

原生主协作菜单、离线发现入口、本地 runtime 和真实本机签名已接通。自动检查使用本地接口和合成参与者；真实 OpenCode 人工体验和真实协作验收仍保留。下一步是独立 Context 材料草稿恢复与逐次读取审计，以及原任务表的通知/评价、运营与发布条件。
