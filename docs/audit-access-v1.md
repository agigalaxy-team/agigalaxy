# 审计查询、导出与独立审批

当前Schema37和覆盖边界见[统一审计覆盖](audit-coverage-v1.md)。以下Schema20及其客户端入口计数为此接口首次交付的历史记录；当前独立客户端为20个入口。

当前Schema20。主体可用明确申请的`audit`会话范围查询自身操作元数据。读取他人记录还要求：读取者在配置名单内、另一位已配置审核者签署限时授权、查询主体和动作位于授权范围内。审核者使用单独的`audit-review`范围。共支持14个可选会话范围，旧会话不会自动扩权；客户端新增`/audit`，共17个入口。动态服务未部署。

## 配置与接口

`GALAXY_GOVERNANCE_CONFIG`新增`auditReaderIds`与`auditReviewerIds`，默认均为空，每组最多32个不同Galaxy ID。配置在启动时读取，不自动热更新。角色名单允许同一人承担不同事项的角色，但每一份授权的审核者与读取者必须不同。拥有会话范围本身不会获得配置角色。

所有接口都是带会话凭据的POST，且已加入Caddy明确路由：

| 路径 | 行为 |
|---|---|
| `/v1/audit/config` | 返回当前主体可用角色与上限，不返回全体角色名单 |
| `/v1/audit/query` | 查询自己或当前获批主体的审计元数据 |
| `/v1/audit/export` | 按同样权限返回当前页JSON、文件名和摘要 |
| `/v1/audit/grants` | 当前主体作为审核者或读取者的最近100份授权，保留撤销记录 |
| `/v1/audit/grants/approve` | 接收`{signed}`，验证审核者签名并保存授权 |
| `/v1/audit/grants/revoke` | 接收`{id}`，原审核者撤销授权 |

查询字段为`subjectId`（缺省本人）、`grantId`（读他人时必需）、`action`、`objectId`（UUID/Galaxy ID/SHA256）、`requestId`、`after`、`through`和`limit`。最多100行，默认25行。游标是十进制字符串，避免bigint精度丢失；客户端携带through读取后续页，不把每次查询新增的审计行不断追入同一次分页。through是序号上界，不是数据库跨事务快照或覆盖未来迟到提交的承诺。

自身记录筛选为actor属于本人，或记录关联binding的主体属于本人；后台组件没有这些关联的记录不猜测归属。只选固定审计列，不返回业务正文、原始Context、Token、凭据哈希或签名内容。未知历史字段仍保持NULL。

## 签署和生效条件

授权载荷包括版本1、UUID、endpoint、reviewerId、reviewerBindingId、readerId、subjectIds（1至16个）、actions（query/export）、reasonCode、issuedAt和expiresAt。有效期最多3600秒，不能超过审核者绑定期限。reasonCode是受限格式事项编号，避免把争议原文塞入审计。

复用jose的Compact JWS，类型`galaxy-audit-approval+jws`，由审核者既有Galaxy身份签名。服务在当前审核者会话事务内验证身份、公钥、绑定、签名、角色名单和期限，保存精确载荷、摘要和签名；相同载荷重试只记一次授权。它是审计专用审批，不是内容发布Consent，也不赋予业务发布、编辑历史或能力认证权。

每次读他人数据，都重新检查读取者角色、审核者角色、原审核绑定的范围/期限/撤销状态，以及授权本身的范围/期限/撤销状态。撤销审核绑定、移出审核者或读取者名单、授权到期或撤销都会阻止后续读取。原审核者即使不再具有新增审批角色，仍可通过自己的有效audit-review会话撤销旧授权。

## 留痕与导出

新增`audit_access_grants`保存批准范围，`audit_reads`保存每次成功查询/导出的调用主体、目标主体、授权ID、准确筛选条件、结果行数和结果摘要。对应`audit.grant`、`audit.grant.revoke`、`audit.query`、`audit.export`写入原audit_events，记录实际调用绑定、客户端、scope、凭据范围与HTTP请求ID。业务结果及留痕在同一事务提交，记录失败时不返回查询数据。

审计操作不虚构内容Consent；Schema20将这四种固定动作明确纳入consent_id为空的完整上下文规则。API可新增授权与读取记录、更新授权撤销时间，不可改写授权载荷、删除读取记录或改删原审计。没有业务接口直接改写历史或发放能力认证。数据库所有者、主机管理员及部署配置的管控仍是运营边界，不能把应用角色限制宣称成对超级管理员的防篡改保证。

JSON导出的sha256覆盖返回快照（不含sha256、filename和mediaType自身）。摘要用于完整性比对；查询记录提供来源追踪，不把普通JSON导出当成独立第三方认证或可离线核验的签名证明。原生入口显示可复制的JSON和文件名，不自动保存到用户目录或发往第三方。

## 原生入口、部署和回退

显式获得audit范围后，连接页第3项显示“绑定与审计”，进入后可查绑定或审计记录；`/galaxy`默认主菜单及L3初始化规则沿用现有行为。审核者可在审计子菜单填写读取者、主体、动作、事项编号与期限，查看精确载荷后一次确认。`createLocalHostRuntime`仅在确认执行期间使用既有本地身份签名，不重新生成ID；退出、取消或本地授权变化会阻止后续执行。

AI agent部署时先确认当前环境和Schema20，再用管理连接执行迁移并应用api-role.sql。角色名单与真实签名/数据库材料从已授权配置提供，不能用测试身份填充运营角色。旧会话重新申请新增范围前只保留原能力。验证查询、错误身份、独立审批、撤销与导出记录，再进行目标宿主人工验收。

回退优先关闭审计代理入口并撤销未完成授权，保留授权载荷、读取记录和历史审计。Schema20不能交给仅支持19的旧服务；采用前向修复或已验证的隔离恢复。当前授权列表是有界最近记录；长周期归档、异地恢复、运营角色变更流程与全部C16/C18验收继续按总计划完成。
