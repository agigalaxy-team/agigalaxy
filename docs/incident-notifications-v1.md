# 事故站内通知 v1

2026-09-10，本地实现。Schema29 / 38表，29个本人导出数据集，19个客户端导出入口；动态服务未部署。

对应 C16-07 的“通知受影响者”。复用站内收件箱、通知偏好和已读记录，新增按主体保存的 `incident_notices`。操作员显式指定每位接收者及说明；普通 API 不提供运营投递接口，也不能写入或改写这些通知。

## 使用者行为

- 收件箱返回本人收到的事故说明、事故ID/版本、运营引用与投递时间；不返回其他接收者名单。
- 支持分页、未读过滤、已读记录及事故通知开关，遵守站内通知总开关。旧偏好未包含 `incidents` 时默认为true。
- contained/recovery 期间通知查询只返回事故通知；原协作、Capsule和材料通知不从该入口泄露业务正文。偏好读取/保存和已读仍可操作。
- 原生菜单展示说明并返回收件箱，不尝试打开不存在的协作。业务总菜单与初始化流程保持不变。
- 本人导出新增 `incident-notices`。事故暂停期间导出入口仍阻断，解除后可导出；站内关闭通知不删除数据。
- 删除清单与通用删除执行器纳入该表；投递命令重试不会重建已经删除的通知。审计保存操作ID和摘要，不保存说明正文。

这里的投递表示数据库内收件箱记录已持久保存。用户仍需主动查询；已读表示用户端确认打开，不证明本人理解。没有邮件、短信或外部聊天推送；关闭通知或失去身份访问的用户需要运营采用另行授权的渠道联系。

## AI Agent 配置和投递

先升级到Schema29并重应用 `packages/galaxy-official/src/infrastructure/api-role.sql`。API仅获得新表SELECT，运营命令通过单独的维护数据库角色执行；不要把维护凭据交给API。现有Worker不需要该表读取权限。

API必须已经加载对应事故ID和版本；投递命令在同一事务中验证最新配置观察记录、插入每位接收者的通知并追加审计。所有目标须是数据库内已有主体；一个目标或通知ID失败，整批回滚。每批最多128条，每条有独立UUID、明确subjectId、最多200字标题和1200字说明。

命令文件字段：

```text
version: 1
id: 本次操作UUID
endpoint: 实际HTTPS origin
incidentId: 已加载事故ID
incidentRevision: 已加载事故版本
operatorRef: 操作员引用
notices: [{id: 通知UUID, subjectId: 接收者Galaxy ID, title: 标题, summary: 私有说明}]
```

使用明确运行环境及独立维护连接配置，执行：

```text
node packages/galaxy-official/scripts/incident-notices.mjs ABSOLUTE_COMMAND_JSON
```

命令只输出操作ID、数量、是否重试和 externalDelivery=false。输入文件属于私有运营材料，不放到公开状态、源码或普通日志。首次投递和恢复进度分别使用新操作ID、新通知UUID；同一操作ID仅用于完全相同的重试。重试已完成操作返回原始投递数量，不表示再次投递，也不会补回后来删除的通知。

恢复与撤销沿用 [事故流程](incident-response-v1.md)。API/Worker 需各自按连续版本加载事故配置；旧Worker未同步时保持隔离。关闭投递CLI或撤去维护写权限可停止新通知；已投递正文保留至数据生命周期处理。不要通过降级Schema或更新原始通知正文回退；纠正说明另投新通知。

## 已验证

本地真实HTTP覆盖本人可见、跨主体已读拒绝、分页、偏好、暂停时接口行为、导出和删除清单；真实 PostgreSQL 的受限 API 角色跑同一流程，并验证不能写入、修改、删除事故通知。

真实 API/Worker 子进程演练证明：加载 contained 后就绪503，Worker已运行暂停迭代但两个到期任务仍保持pending且attempts=0；同ID下一版本 resolved 后API就绪200，Worker恢复处理，已撤销证据未升级、未产生Proof，并正常停止释放连接。测试均使用临时集群和合成身份，没有真实外部来源访问。
